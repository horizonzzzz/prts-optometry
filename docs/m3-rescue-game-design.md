# M3 营救行动 · 设计与实现方案

> 状态：玩法方案草稿；PRTS 菜单与 Phaser 验证场已初步实现
> 适用范围：本仓库新增的第二个可玩游戏、配套纸质卡片物料
> 最后更新：2026-10-27

## 1. 文档目的

本文件记录「M3 营救行动」物料与网页小游戏的当前方案，包括：

- 为什么做这个游戏、它和仓库里已有的验光游戏是什么关系
- 游戏的规则、流程、关卡与物理参数
- 纸质卡片物料的具体规格与文案
- 在本仓库中的实现方式与目录结构
- 已确认的决策、待确认的问题、以及已知风险

本文面向实现者（包括未来的自己）。玩法方向和物料概念已确认；具体参数、关卡细节与制作顺序仍需通过原型和试玩验证。本文记录当前决策与待验证假设，不把未经测试的数值视为最终规格。

## 2. 一句话概念

一张倒着印的《代管责任书》卡片，扫码进入一款坑向平台跳跃游戏：你代管的黑色小猫 M3 跑掉了，你操作小猫在阳光下的罗德岛舰桥与甲板间跑跳，营救被倒挂的博士和其他干员；一路被凯尔希回收，再重新出发。流程长度由原型试玩和后期制作决定，不设固定时长。

## 3. 已确认方向与初步约束

| # | 决策 | 理由 |
|---|---|---|
| 1 | 复用本仓库，新增首页选择游戏，原验光游戏保留 | 共享构建、路由与部署；M3 保持独立美术与游戏界面 |
| 2 | 新游戏是**重玩法轻剧情**，与验光游戏的**重剧情轻玩法**形成对照 | 两个游戏并排放置时不能是同一种体验 |
| 3 | 以 iwanna（GM8）移动语义为手感参考，以猫里奥式视觉欺骗为关卡风格 | 物理参数由原型调定；陷阱以场景线索和少量纯欺骗组合，避免把误操作当成难度 |
| 4 | **纯即死判定**，没有血量、没有护盾、没有击退 | 简化状态机；坑向类型依赖即时重开 |
| 5 | 死亡统一解释为**回收**：凯尔希抓住 M3，不是 M3 死了 | 避免 OOC，让失败可无限重复且不需要任何设定说明 |
| 6 | 场景地基是**甲板 / 货舱 / 管道**，不是医务室 | 避免与验光项目的白色诊室视觉重复 |
| 7 | 先做 6 个主要区域；第 7 区回程作为可选扩展；死亡回到当前区域起点，不设检查点 | 先验证核心流程，再决定是否扩展回程内容 |
| 8 | 全场只给**一个能力**（二段跳），在货舱区域救下极境后解锁 | 单一能力聚焦平台跳跃操作，并形成清晰的前后关卡变化 |
| 9 | M3 使用黑色身体、绿色眼睛的猫形象方向 | 剪影便于辨认和碰撞判断；具体采用哪一版社区二创形象及素材来源需先确认 |
| 10 | 卡片**上下颠倒印刷** | 与游戏目标（把倒挂的人放下来）同构，零成本且无人重复 |
| 11 | 二维码**全场统一一个 URL**，编号栏留空由玩家自填 | 游戏不使用唯一编号；可变数据会增加印刷制作和校对环节 |
| 12 | 画面**横屏优先**：16:9 逻辑分辨率 768×432（48×27 格），竖屏触屏只显示旋转提示 | 横版跳跃的预判方向在水平轴；左右拇指分区覆盖式按钮不遮挡主视线；原 1:1 竖屏方案被推翻（见 9.6） |

## 4. 世界观与角色

### 4.1 凯尔希与 M3

凯尔希是主人，M3 是小猫。这个关系不是压迫性的，是"管教"性质的：M3 犯了事，被叫回来，被拎起来，仅此而已。

这个设定决定了两件事：

- **凯尔希全程不动手、不失态**。她不需要当反派，她只需要是那个"负责把猫抓回来的人"。台词永远是公文腔，不超过十个字。
- **失败不是惩罚，是复原**。M3 被抓住之后没有受伤，只是回到主人手上，然后下一次又被放出去。逻辑上完全自洽，玩家也不会因为反复失败而产生"这个角色很惨"的负面情绪。

### 4.2 M3 的形象

形象方向参考社区二创中的**黑色小猫 + 绿色眼睛**样式；具体设计与素材来源需先确认。该方向的优点是：

1. **轮廓稳定**。黑色身体便于在浅色甲板上辨认，也便于制作待机、跑、上升和下落状态。
2. **碰撞边界清楚**。平台跳跃需要玩家容易判断角色与地形的相对位置，保持角色剪影简洁。
3. **失败画面有表现空间**。被拎起的 M3 可以在同一张失败图中画得更具动物感，与关卡内的简化造型形成区别。

**视觉规范**：

| 部位 | 处理 |
|---|---|
| 身体 | 纯黑 `#0A0E12`，不加描边，靠背景对比突出 |
| 眼睛 | 两点绿色发光 `#4ADE80`，是全身唯一的高光 |
| 耳朵 | 尖三角形，两个 |
| 尾巴 | 细长，带轻微摆动，是分辨动作方向的主要依据 |
| 尺寸 | 约 16×16 px（一个瓦片），判定位略小于视觉 |

M3 眼睛使用绿色 `#4ADE80`。现有 `src/optometry/optometrySceneModel.ts` 的 `COLORS.originiumSoft` 是琥珀金色，不适合当作绿色来源；本作颜色在 `src/m3/render/theme.ts` 单独定义，避免误用现有 token。

**素材与权利确认**：黑猫绿眼是社区二创方向，不是官方设定。制作前先确认具体形象的创作者、来源和许可条件；标注来源与非官方声明不能替代授权。若无法确认可用范围，改用自行设计且不直接复刻该社区形象的猫形象。

### 4.3 其他角色

| 角色 | 位置 | 作用 |
|---|---|---|
| 极境 | 第 3 屏结尾，倒挂在吊架上 | 被救后给予二段跳。他是唯一被救的人 |
| 博士 | 第 6 屏，倒挂在甲板吊臂上 | 终点。救到即通关 |
| 可露希尔 | 不出现立绘，只以文字出现 | 失败次数过多时给提示，见 6.3 |

**为什么只救一个人**：让极境的救援同时承担能力解锁，让博士承担终点目标，两个角色各自对应一个明确的流程节点；增加更多被救角色前，先验证现有节奏是否需要扩展。

## 5. 核心规则

### 5.1 唯一失败方式

**任何失败都等于"被回收"**，不区分原因：

- 碰到凯尔希的陷阱 → 被抓住 → 回收
- 掉出甲板 / 掉进深渊 → 回收
- 被货柜扣住 → 回收
- 走到假终点 → 回收（并且是最好笑的一次）

游戏里不存在"受伤"、不存在"扣血"、不存在"击退"。玩家只有两种状态：**在走** 和 **被拎起来**。

### 5.2 重开机制
- 不设暂停菜单或全局检查点；刷新页面或重新开始会从头开始
- 失败时显示同一张静态失败图和一个「重试」按钮，不按失败原因切换画面
- 点击或通过键盘激活按钮后，从当前区域起点重新开始
- 不自动重开，也不设置强制停留时间；失败画面不播放台词、随机位移或姿态动画
- 重试时清空本次操作输入，避免按住的方向键或触摸状态带入新一轮

失败次数在流程状态中累计，结算时再显示；失败画面本身只保留一张图和一个重试按钮。
### 5.3 状态

本轮游戏的流程状态只保留玩法所需数据，不写入 `localStorage`：

```ts
type Progress = {
  screenIndex: number; // 0..5；若实现可选回程区则使用 6；区域内回到能力门不改变编号
  hasDoubleJump: boolean; // 救下极境后变为 true
  recallCount: number; // 本轮累计被回收次数
};

type RunMeta = {
  consecutiveRecallsByScreen: Record<number, number>;
  hintedScreens: number[];
  triggeredTraps: string[]; // 可选回程区用
};
```

`RunMeta` 记录区域连续失败次数和已显示提示的区域；若制作可选回程区，再记录已触发的陷阱 ID，以便返程时改变其状态。所有数据都只在本轮内存中有效，不构成存档。

每次死亡保留流程状态，只重置当前区域的玩家位置、速度、接地状态、土狼时间、跳跃缓冲和重试输入；成功离开区域后重置该区域连续失败次数。刷新页面或重新开始会从头开始。
### 5.4 失败预算

- **不设固定失败次数目标**。总回收次数与各区域失败分布用于试玩调节难度，不作为通关或发布门槛
- 每区域 3–5 个坑、总数 20–25 个暂作关卡编排的起始估算；实际数量根据原型试玩删改，不要求凑数

## 6. 失败界面

失败时统一显示一张静态图和一个「重试」按钮，不按失败原因、次数或关卡切换内容。失败次数与评级信息留在结算界面，不放进失败界面。

### 6.1 静态画面

- 一张像素风画面：凯尔希面无表情地拎着 M3，背景使用纯色或简化的甲板
- 画面不做动画、不随机变化、不叠加台词、次数或额外操作项
- 同一张图贯穿整轮游戏；失败原因统一解释为 M3 被回收

### 6.2 重试

- 失败后暂停当前区域，显示上述静态图和一个真实的「重试」按钮
- 激活按钮后，从当前区域起点重开；重试前清空方向键、跳跃键及触摸按压状态
- 不自动重开、不设强制停留时间；按钮同时支持指针操作与键盘焦点、Enter/Space 激活
- 失败界面的可访问名称由图片替代文本和按钮名称提供；Canvas 继续保持 `aria-hidden`

### 6.3 可露希尔的提示

同一区域连续失败 8 次后，在下一次点击「重试」进入的游戏画面底部显示一条针对该区域难点的提示。提示不属于失败界面，也不改变重试操作。

```text
可露希尔 › 左边那面墙是假的。
```

- 每个区域每轮游戏最多显示一条；提示显示后记录该区域已提示
- 成功离开当前区域后，连续失败计数清零
- 先按同一区域连续失败 8 次实现；试玩后再调整阈值

可露希尔不救玩家，只提供破解信息。
## 7. 流程结构

### 7.1 关卡地图

逻辑分辨率 **768×432**（16:9，横屏优先），瓦片 **16×16**，即每屏 **48×27 格**。

```
  屏 1  甲板前沿      教学 + 系留索 + 警示带
  屏 2  甲板边缘      侧风 + 探照灯
  屏 3  货舱          能力门（先不可达）+ 救极境 → 解锁二段跳
                     回到本屏能力门并通过
  屏 4  货舱下层      假平台
  屏 5  维修管道      磁力区 + 假终点
  屏 6  引擎区        真终点，救博士
  屏 7  逃回（可选）  通关后原路返回，陷阱状态改变
```

### 7.2 每屏设计要点

**屏 1 · 甲板前沿**

- 目的：让玩家在试玩过程中理解跑、跳和失败重试；教学节奏由实际体验验证
- 第一个坑必须是**警示带**：看着是装饰、踩上去会弹飞、直接掉出甲板
- 第二个坑是**系留索**：一片绷紧的防水布，看起来和地板一模一样，踩上去塌进吊货网
- 屏 1 不给任何提示文字。第一个坑骗到玩家，游戏就成立了

**屏 2 · 甲板边缘**

- 引入**侧风**：持续横向推力，跳跃距离变短，但不会直接害死你
- 引入**探照灯**：光扫过身体时进入锁定，2 秒后回收。给玩家一个可观察的前摇
- 这一屏的难度来自"两个机制叠加"而不是单点精度

**屏 3 · 货舱**

- **货柜陷阱**：走过去，头顶货柜落下扣住你。有前摇，可以被观察
- **能力门**：在货舱区域提前展示一段当前跳不上去的平台；玩家先走可通过的下层路线，救下极境获得二段跳后，回到同一区域通过这段平台
- 极境位于该区域的支路尽头；救援后保留二段跳，再返回能力门
- 能力门和救援点都属于屏 3，区域内回走不增加检查点；死亡仍从本区域起点重开
- 关键能力门在首次经过时必须可见，让玩家能把后续解锁和早先障碍联系起来

**屏 4 · 货舱下层**

- 通过屏 3 的能力门后进入货舱下层
- 引入**假平台**：画着却会掉。这是猫里奥的第一课
- 屏 4 是玩家第一次感到"我变强了"，节奏要快，坑要少

**屏 5 · 维修管道**

- **磁力区**：M3 被吸住，移动变慢、跳跃变矮。不是即死，但会把你逼进即死
- 狭窄的单向通道，不能回头
- **假终点**：倒挂着一个"博士"，走过去才发现是货箱。走进去 = 回收
- 这是全场唯一一个叙事型坑，只能出现一次

**屏 6 · 引擎区**

- 最后一段，难度回到中等，让玩家顺利通过
- 真博士倒挂在吊臂上
- 救到 → 凯尔希出现，什么也没做，只说一句「……下课了。」之类的收尾（或者干脆不说话，画面切黑）
- 结算：`RECALL 计数` + `S/A/B/C 评级`

**屏 7 · 逃回（可选，首版暂缓）**

- 救到博士后进入可选回程；不加入新陷阱，复用前面区域的素材
- 先完成并试玩屏 1–6，再决定是否实现；不设固定游玩时长
- 回程中已经触发过的陷阱保持失效，尚未触发的陷阱继续生效；状态按陷阱 ID 保存在本轮内存中

### 7.3 评级

| 回收次数（初始阈值，试玩后调整） | 评级 |
|---|---|
| ≤ 8 | S |
| 9–14 | A |
| 15–22 | B |
| ≥ 23 | C |

评级的作用是给玩家重玩理由，同时和卡片衔接：结算界面的评级，就是卡片背面「评定结果 ___」那一栏应该填的东西。

## 8. 陷阱清单

全部是"抓住"，没有一个是"杀伤"。

| 代码 | 名称 | 表现 | 前摇 | 用途 |
|---|---|---|---|---|
| `X` | 系留索 | 一片绷紧的防水布，长得像地板，踩上塌进吊货网 | 无（纯欺骗） | 猫里奥式视觉骗局 |
| `C` | 吊臂货柜 | 头顶货柜落下扣住 | 有（钢索振动 0.3s） | 可观察的坑 |
| `L` | 探照灯 | 光扫过身体，2 秒后锁定回收 | 有（光束移动） | 给跳跃加节奏维度 |
| `T` | 警示带 | 看着是装饰，实际会反弹把人弹飞 | 无 | 最便宜的一种坑 |
| `E` | 通电地砖 | 黄黑警示纹那几块会通电，纹路很淡 | 有（电流声） | 考验观察 |
| `M` | 磁力区 | M3 被吸住，移速减半、跳跃高度减半 | 可见的磁场粒子 | 不是即死，是压力 |
| `W` | 甲板侧风 | 持续横向推力 | 可见的风向粒子 | 同上 |
| `D` | 假终点 | 倒挂的"博士"其实是货箱，走进去即回收 | 无 | 全场唯一，只能出现一次 |

**设计约束**：陷阱融入正常场景，不加悬浮提示图标、警告符号或高亮描边。需要可观察前摇的陷阱，使用场景内线索（如钢索振动、扫动光束、电流声）；纯欺骗陷阱只用于少数惊吓点，并在试玩中确认玩家能区分“看漏线索”和“操作失灵”。

## 9. 物理与手感

### 9.1 GM8 跳跃模型

手感参考 GM8 的**移动语义**。以下是本方案拟采用的起点模型，参数与更新顺序仍需通过固定步长原型验证：

```text
1. 落地 && 本帧按下跳跃
        → vspeed = -JUMP

2. 按住 && 上升中 && 已按住帧数 < HOLD_FRAMES
        → vspeed = min(vspeed, -JUMP)        // 锁定上升速度，抵消重力

3. 本帧松开 && 上升中 && 尚未削减
        → vspeed = max(vspeed, -(JUMP - CUT)) // 只削 CUT

4. 每帧
        → vspeed = min(vspeed + GRAVITY, MAX_FALL)

5. 水平方向
        → hspeed = ±RUN_SPEED 或 0            // 瞬时，没有加速度，没有惯性

6. 积分
        → x += hspeed;  y += vspeed
```

以下三点是本方案希望保留的 iwanna 风格操作特征：

- **水平方向没有加速度**。按下方向键的瞬间就是满速，松开就是零。
- **上升期有 HOLD 帧的速度锁定**，把上升速度钉住并抵消重力。这是 iwanna 起跳"很冲"的原因。
- **松键只削减 `CUT`（1 个单位）**，不是常见的砍半。跳多高几乎完全由按住帧数决定。

**如果按常规教程写成「松键时 `vspeed *= 0.5`」，手感会立刻变成马里奥。** 这是最容易犯的错误。

### 9.2 起点参数（60Hz）

GM8 的物理按步长积分，同样的数值在 30fps 和 60fps 下是两种游戏。本项目使用 **60Hz 固定步长**。

换算关系（保持同样的弧线）：

```text
v60 = v30 / 2
g60 = g30 / 4
按住帧数(60) = 按住帧数(30) × 2
```

| 参数 | 值 | 说明 |
|---|---|---|
| `GRAVITY` | 0.6 | 每帧 |
| `JUMP` | 9.0 | 起跳瞬时速度 |
| `MAX_FALL` | 9.0 | 与 `JUMP` 相等，限制最大下落速度 |
| `RUN_SPEED` | 3.5 | 恒定，无加速度 |
| `HOLD_FRAMES` | 4 | 起跳后锁定帧数 |
| `CUT` | 1.0 | 松键削减量 |

当前弧线不能只用 `JUMP² / (2 × GRAVITY)` 直接定稿：这个连续近似忽略了 60Hz 离散积分、按住跳跃时的 `HOLD_FRAMES` 速度锁定和提前松键时的 `CUT`。该公式只能作为不含速度锁定时的粗略参照，不能据此断言实际最高点或滞空时间。

**调参锚点**：先实现固定步长的移动模型，用自动化测试按实际更新顺序计算起跳、按住、松键和落地的轨迹；再选定目标跳高和跳远，根据实测能力设计关卡。玩家的空间认知应建立在稳定、可预测的实际跳跃上，而不是连续公式的近似值。

水平速度 `3.5 px/帧 @60Hz` 对应 `210 px/s`，约 `13 格/秒`；同样需在目标设备上确认是否容易观察和控制。
`MAX_FALL` 与 `JUMP` 相等只限制最大下落速度，并不保证含有跳跃保持和松键削减的实际弧线严格对称。若希望更重的下落感，可以在试玩后调整 `MAX_FALL`，并同步更新轨迹测试。

### 9.3 额外增加的两个机制

原版 iwanna 没有土狼时间和跳跃缓冲，因为它靠键盘精度和关卡设计来弥补。**但本游戏的主入口是手机扫码**，触摸的精度天花板明显更低，所以这两个必须加：

| 机制 | 帧数 | 作用 |
|---|---|---|
| 土狼时间 | 5 帧 | 离开平台后仍可起跳 |
| 跳跃缓冲 | 5 帧 | 落地前提前按跳会被记住 |

两者只抬高容错下限，不降低操作上限。这两条不加，手机玩家会在"我明明按了"上反复受挫，而那种受挫和坑向类型的乐趣完全无关。

### 9.4 碰撞

- 使用 **Phaser Arcade Physics** 负责矩形碰撞与分离，不再自写完整碰撞引擎，也不引入 Matter.js / planck.js。
- 保留 Arcade 默认 `forceX = false`，按主重力方向优先分离；贴墙下落、撞顶与落地必须在实际 Arcade 场景中验证。
- **单向平台**：结合碰撞面配置与 collider 的 `processCallback`，只接受下落且上一物理步脚底在平台上方的接触。
- 落地判定留 **1 px 容差**；固定步中检查接地状态，不能把渲染帧作为物理帧计数。
### 9.5 输入

| 平台 | 方案 |
|---|---|
| 键盘 | 方向键 / A·D 移动，空格 / Z / ↑ 跳跃；按键按下与松开都更新输入状态 |
| 触摸 | 画面左下角「←」「→」与右下角「跳跃」**覆盖式**真实按钮；按住持续输入，松开立即停止 |

三个按钮需支持多点同时按压，处理 `pointerup`、`pointercancel`、窗口失焦、组件卸载与orientation 变化时的状态清理，并设置 `touch-action: none` 防止游戏区域滚动。按钮使用稳定尺寸和足够间距；键盘和触摸共用同一输入快照。无需虚拟摇杆。
触摸按钮须允许按住跳跃来控制跳跃弧线，并可靠处理松开和系统取消事件；具体按钮位置、尺寸与左右手操作舒适度以真机试玩为准。

### 9.6 帧率与画布

- 逻辑分辨率 **768×432**（16:9），横屏优先
- 画布缩放交给 Phaser **Scale FIT + CENTER_BOTH**：按宿主容器等比缩小放并居中，超宽屏左右留白、4:3 屏上下留白，留白区使用晴空渐变承接；宿主铺满视口，不裁切关卡，不拉伸画面
- 竖屏触屏设备（`(orientation: portrait) and (pointer: coarse)`）显示整幅「请将手机横屏游玩」遮罩并阻断触控；桌面竖窗口不受影响。浏览器无法强制横屏（Screen Orientation API 仅全屏/安装态可用），因此只提示不强制
- 固定步长 60Hz，渲染每帧最多补 5 步（防止死亡螺旋）

**为什么改为横屏优先（推翻原 1:1 方案）**：原方案为迁就扫码后手机默认竖屏姿态而选择 1:1，避免强制旋转。改为横屏的理由：①平台跳跃的预判主要发生在水平轴，48 列的可视距离比 30 列从容得多；②覆盖式左下/右下按钮把拇指操作移出主视线，替代原方案“画布下方按钮”对竖向空间的挤压；③探照灯、货柜下落等陷阱前摇的观察窗口本质是横向时间窗。代价是竖屏入口多一步旋转动作，用遮罩提示承接，不做强制旋转。

## 10. 视觉设计

### 10.1 独立的暖色平台游戏

M3 是搞笑风格的横版平台游戏，讲述小猫营救博士和其他干员。参考《超级玛丽》《索尼克》的明亮、易读场景与《死亡细胞》的前后景层次，不照搬其素材或默认沿用暗色美术。游戏内不使用 PRTS 终端页眉、页脚、系统编号或诊断文案。

- 搞笑感通过角色姿态、救援处境和关卡机关表达；不加入终端监测面板、虚构血量或尚未实现的救援计数。

### 10.4 AI 生成约定

1. **目录**：`assets/ai/`，与官方素材分开存放
2. **命名**：`<场景>-<用途>-<序号>.png`
3. **格式**：统一透明背景 PNG，准备 1x / 2x 两套，按 Phaser 场景缩放需求导出，避免重复采样模糊
4. **可复现记录**：在 `assets/ai/ATTRIBUTIONS.md` 中记录每张图的模型、prompt、生成日期。结构参照现有的 `assets/audio/ATTRIBUTIONS.md`
5. **禁止**：不要让 AI 直接生成带官方立绘角色大面积正脸的画面。需要角色时优先用剪影、背影、局部

第 5 条的理由是版权而不是画质。失败画面里的凯尔希必须是像素风、简化过的，不能是"还原立绘"。

### 10.5 动效与可访问性

沿用仓库现有约定（参见 `AGENTS.md` 的 Motion / a11y 一节）：

- 遵守 `prefers-reduced-motion: reduce`：取消视差滚动、取消屏幕震动，保留关卡推进和最终画面
- Canvas 保持 `aria-hidden`，移动和跳跃控件使用真实的 `<button>` 覆盖在上面
- 失败时通过可访问的静态图片替代文本和「重试」按钮名称传达状态；不再使用失败台词 live region

### 11.3 为什么倒着印

这是整套物料里成本最低、记忆点最强的一个处理：

- 玩家的第一个动作就是**把一个倒着的东西扶正**，而游戏的目标是**把倒挂的人放下来**。同一个动作。
- 翻转之后才发现正文是"代管责任书"，而卡片最底边写着"已走失" —— 顺序本身就是一个小机关。
- 零成本。印刷厂只是把文件旋转 180 度。

### 11.4 二维码策略

**一个二维码，所有卡通用。**

不做可变数据（每张卡不同编号）：游戏不使用唯一编号，加入编号只会增加印刷文件生成和逐张校对工作。编号栏留空，由玩家自行填写。

取而代之：**编号栏留空，让玩家自己填。**

- 二维码统一指向 `https://<域名>/#/m3`
- 玩家扫进来，游戏开头不询问任何信息
- 结算界面的评级，对应背面那行「评定结果 ___」

这样一张卡就是一份真的"签收单"——要先签字，才生效。

### 11.5 印刷前必须做的验证

1. **哑膜上的 15mm 二维码对比度**。哑膜会压低对比，必须实物打样后用三台不同手机实际扫描。
2. **倒印的文件在印厂会不会被自动"纠正"**。交付文件时在文件名和沟通中明确标注"此文件为最终印刷方向，请勿旋转"。
3. **先印 50 张**，确认扫描和手感之后才批量。

## 12. 技术实现

### 12.1 在本仓库中的位置

复用 React、路由、字体与部署体系，新游戏使用独立引擎：

- React 19 + React Router 7 + Vite 8 + TypeScript 7
- 验光：PixiJS 8；M3：**Phaser 4.2.1 + Arcade Physics**，依赖固定版本
- 样式使用独立的 `src/styles/m3.scss`，Phaser 配色在 `src/m3/render/theme.ts`；不导入 PRTS 终端样式
- 部署沿用 Cloudflare Workers（`wrangler.jsonc`）

Phaser 接管 Scene 生命周期、资源、动画、基础物理积分和 AABB 碰撞。跳跃保持、CUT、土狼时间、跳跃缓冲与流程状态保留为独立 TypeScript 逻辑。React 继续提供真实按钮、失败层和路由。

不再维护第二套自写碰撞系统；不引入额外物理引擎或关卡编辑器。先用 ASCII 地图，待文本维护成本确实过高时再评估 Tiled。
### 12.2 路由

**现状**（`src/main.tsx`）：

```
#/             → OptometryPage
#/legacy-dom   → LegacyDomPage
其他           → 重定向到 #/
```

**风险**：如果光栅卡上已经印出去的二维码指向 `#/`，把根路径改成首页会让老卡失效。本次保持根路由；今后若要替换根入口，必须先实际扫码确认。

本次采用方案（保留旧入口）：

```
#/             → OptometryPage      （保持现状，老二维码继续有效）
#/m3           → M3RescuePage        （新游戏）
#/index        → IndexPage           （首页，游戏选择）
#/legacy-dom   → LegacyDomPage
```

并在 `OptometryPage` 的入口首页加一个不显眼的 `INDEX` 入口通向 `#/index`；进入验光流程后隐藏，避免遮挡画面。

如果确认老二维码指向的是 `#/vision` 之类带路径的地址，则可以自由地把 `#/` 改成首页。

### 12.3 目录结构

沿用 `src/pages/`，M3 位于 `src/m3/`。仓库已按游戏拆分目录：验光在 `src/optometry/`（PixiJS，含 `state.ts`），M3 在 `src/m3/`（Phaser），两者只共享构建、路由、字体与部署。

```text
src/
  pages/
    IndexPage.tsx          # PRTS 总菜单，轻量 DOM
    OptometryPage.tsx      # 验光宿主：Pixi canvas + 真实按钮
    M3RescuePage.tsx       # React 宿主、真实按钮、失败层
  optometry/               # 验光游戏，PixiJS
    state.ts               # 验光 stage/mute 状态机
    createOptometryScene.ts
    optometry*Scene.ts
  m3/
    core/
      rules.ts             # 参数与时间单位换算（含 768×432 / 16:9 逻辑分辨率）
      loop.ts              # 60Hz 累加器，每渲染帧最多 5 步
      input.ts             # 按来源合并键盘与多点触控
      movement.ts          # 跳跃计时与速度决策，无 Phaser 依赖
      progress.ts          # 回收与重试状态，无 Phaser 依赖
    world/
      level.ts             # 48×27 ASCII 校验与解析
      sandbox.ts           # 基础操作验证场（横向路线），不代表正式第一区
    render/
      theme.ts             # 新游戏独立色彩
      drawScene.ts         # Phaser 程序绘制占位素材
    createM3Scene.ts        # Phaser Game / Scene、Arcade 适配和销毁
    core.test.ts           # 手感、输入、补帧、状态和地图测试
```

### 12.4 硬性架构约束

**`core/` 和 `world/` 不导入 Phaser 或 PixiJS。** 核心只接收数值和输入快照，输出速度决策与状态；Arcade Body、collider 与 Game 的操作留在场景适配层。

- Phaser 仅通过 `M3RescuePage` 的 lazy 路由加载；总菜单不初始化任一引擎。验光页继续使用 PixiJS。
- Arcade 关闭自动 update，使用 60Hz 累加器驱动 `world.update()`；手感决策在每次物理步前执行，接地/触发在物理步后读取。最多补 5 步，额外积压丢弃。
- 画布缩放交给 Phaser `Scale.FIT + CENTER_BOTH`，宿主元素撑满可用区域；除 `image-rendering: pixelated` 外不用 CSS 拉伸 canvas。触屏竖屏由 CSS 遮罩提示旋转，输入层在 orientation 变化时清空。
- 文档物理值为 px/帧：速度乘 60，重力乘 3600 转为 Phaser 的 px/s 与 px/s²，不能直接照搬数值。
- 路由卸载清理输入和监听器，并调用 `game.destroy(true)`；不得使用禁止再次创建实例的 `noReturn=true`。销毁由 Phaser 下一帧处理，需验证快速退出和重进。
- Vitest 测纯逻辑；真实碰撞、生命周期和触摸需要浏览器集成验证。纯函数测试不能替代 Arcade 场景检查。

## 14. 已知风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **跳跃手感不符合预期** | `HOLD_FRAMES`、`CUT` 和离散积分共同决定弧线，连续公式不能准确给出跳高 | 先实现确定性固定步长模拟和轨迹测试，再用键盘与手机试玩调参 |
| **触控输入不稳定** | 浏览器手势、触点取消或失焦可能让按键状态卡住，窄按钮也会误触 | 使用三个真实触控按钮，处理取消/失焦并支持多点按压；目标手机实际通关 |
| **重试操作打断节奏** | 每次失败都要手动按按钮，重复尝试时可能显得拖沓 | 保留用户要求的单一静态失败图和「重试」按钮，不加动画或等待；通过试玩判断按钮位置和操作节奏 |
| **难度与流程节奏未校准** | 关卡数量、失败次数和完成时长目前都只是估算 | 不设固定时长或失败次数门槛；记录试玩数据并据此调整区域数、陷阱和提示 |
| **M3 形象辨识度不足** | 低细节剪影可能无法让玩家辨认角色 | 原型中检查轮廓、绿色眼睛和动作方向是否清晰；先确认具体形象来源再制作素材 |
| **二创素材许可不清楚** | 标注来源或写免责声明不代表获得使用许可 | 制作与印刷前确认创作者、来源及授权条件；不明确时使用原创形象 |
| **与验光游戏视觉撞车** | 两个项目都使用罗德岛背景，容易显得像同一套界面换色 | 本作采用晴天暖色舰桥与平台场景，使用独立游戏内控件，不套用终端页眉页脚 |

## 15. 实施顺序

按这个顺序，每一步都能单独看到东西：

1. `core/rules.ts`、`core/loop.ts`、`core/movement.ts` 和 Phaser + Arcade 色块场景：固定步长下能跑、跳、落地
2. 写跳跃轨迹自测，按实际离散积分和跳跃保持/松键逻辑调参；在手机上验证可控性
3. 实现键盘与三按钮触控输入，覆盖多点按压、取消和失焦清理
4. 加一个陷阱、失败计数、单张静态失败图和「重试」按钮；验证重试保留与重置哪些状态
5. 完成屏 1–3 的色块关卡，验证极境救援和区域内返回能力门的路线
6. 完成屏 4–6，并用手机从头通关
7. 加游戏选择页和路由，确认旧二维码仍可用
8. 完成结算评级与可露希尔提示；评级阈值由试玩校准
9. 试玩后决定是否增加屏 7 回程，再替换正式素材
10. 确认形象许可、二维码和版面后打样印刷

先验证移动、跳跃、触控和重试的基本体验，再扩展关卡与美术；不以固定开发天数或游玩时长作为完成条件。

## 16. 当前原型与后续范围（2026-10-27）

本次先交付 PRTS 总菜单与 Phaser 基础操作验证场，不把验证场当作正式第一区。

- `#/m3`：768×432（16:9）横屏验证场，键盘与覆盖式三按钮触控、竖屏触屏旋转遮罩、60Hz 物理步、实体砖、单向平台、回收与手动重试、出口完成层。

- 角色和失败图均为程序绘制的静态占位图，不使用未确认许可的社区形象素材。
- 未完成：正式六区、救援与能力解锁流程、特殊陷阱、正式失败插图、评级、提示及真机手感校准。

采用 Arcade 默认垂直优先分离：实测强制 `forceX=true` 会把相邻地砖接缝误判为侧墙。离散轨迹起点实测长按跳高约 88.2 px，按住 1 帧跳高约 57.8 px；这些是当前参数结果，不是最终手感目标。
